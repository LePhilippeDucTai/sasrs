# Review SAS semantics and conformance

1. Read applicable repository instructions, `CONTRIBUTING.md`, `docs/support-contract.md`, `conformance/README.md`, `conformance/schema.md`, `conformance/STATUS.md` and the relevant implementation/tests. Resolve active plan references through CONTRIBUTING; do not use deprecated `sasrs-impl`, the frozen M1–M66 roadmap or old V2 contracts as a work queue. Reuse the existing corpus and runner instead of adding parallel validation machinery.
2. Scope one DATA/PROC/SQL/macro/format/ODS behavior: write a **minimal SAS reproducer**, inputs, and expected datasets/types, missing values, variable/row ordering, log, listing, diagnostics and return code as applicable. Separate review-only requests from authorized repairs.
3. Obtain expected behavior from a source independent of the implementation: precisely cited SAS documentation, captured SAS output, or an oracle produced by another party as required by CONTRIBUTING §2. A second algorithm written by the implementer is not sufficient as the sole oracle. Record source, author when relevant, SAS version/options and derivation in the case's existing provenance fields or referenced evidence. Check the source actually establishes the tested behavior; do not infer SAS defaults from a generic statistics library or fabricate a SAS run. If evidence is absent or conflicting, report the gap and withhold the validated-against-reference claim.
4. Use `conformance/schema.md` for fixture structure and absolute/relative tolerances fixed with justification before comparing output. Preserve exact character/missing-value semantics and specified ordering; do not sort away a semantic mismatch. Distinguish `validates: math` from `sas-behaviour`: mathematical agreement alone does not establish SAS semantics. A self-generated snapshot proves stability, never SAS conformity.
5. When repairs are requested, fix the smallest demonstrated gap and add regressions. Unsupported or recognized-but-ignored constructs must yield the support contract's ERROR/WARNING rather than a silent fallback. Never alter a `known-divergence` case's expected values as the implementer; when the unchanged reference passes, explicitly promote its status with the required issue justification. Do not loosen tolerances or regenerate expectations from sasrs to obtain a pass.
6. Execute the relevant `scripts/check.sh` suite with `CI=true` and `INSTA_UPDATE=no`, `cargo test --locked -p sasrs --test conformance`, and `python3 scripts/conformance_report.py --check` for corpus changes. Regenerate `conformance/STATUS.md` through its generator, never manually. Follow CONTRIBUTING's per-fixture `Snapshot:` commit justification; ensure tests leave no `.snap.new` or unexpected changes. Before merge, require `ci-ok` on the exact latest PR commit.
7. Report implemented, validated against reference, documented approximation or unsupported using CONTRIBUTING's definitions, with provenance, executed checks and gaps in French. Scope every claim to the behavior and evidence actually checked.

Do not change generated plan views, publish releases or commit without explicit instruction.
